## 1. Rà soát hiện trạng trước khi code

- Chưa có bất kỳ hạ tầng PDF nào trong repo (không PDFKit/Puppeteer/jsPDF...), chỉ có Excel export
  (`exceljs`).
- `Document.signedBy` là field CHẾT — có trong model/interface nhưng KHÔNG service nào từng ghi giá trị
  (grep xác nhận). Dữ liệu phê duyệt THẬT nằm ở `WorkflowInstance.steps[]` (`approvedBy`/`approvedAt`/
  `comment`), đã có sẵn cách populate đúng ở `workflow.service.ts::getWorkflowHistoryForUser`.
- Không có logo/letterhead/con dấu nào trong repo.
- Excel export hiện chỉ hỗ trợ 3 subType PROPOSAL (`meta.items[]` có shape cố định); REPORT/MANUAL có
  `meta` tự do.

## 2. Xác nhận scope với user (AskUserQuestion, nhiều vòng) trước khi code

1. **Phạm vi subType**: user chọn **"Tất cả category/subType"** (rộng hơn Excel export) — bao gồm cả
   REPORT (CHECK_DAMAGE/CONFIRM_STATUS) và MANUAL (`meta` không có shape cố định).
2. **Nội dung "chữ ký"**: user chọn ban đầu **"Cần cơ chế ký số thật"**.
   - ⚠️ Đã DỪNG LẠI cảnh báo rủi ro pháp lý trước khi code: ở Việt Nam, "chữ ký số" có giá trị pháp lý
     (Luật Giao dịch điện tử) bắt buộc gắn với chứng thư số do CA được cấp phép (VNPT-CA/Viettel-CA/FPT-CA/
     BKAV-CA...), KHÔNG thể tự xây nội bộ mà có giá trị pháp lý thật. Tự xây "trông giống" chữ ký số
     (self-signed) mà không nói rõ sẽ gây hiểu nhầm nghiêm trọng nếu dùng cho hồ sơ chính thức.
   - Hỏi lại vòng 2 với 3 mức độ cụ thể → user chọn **"Ký nội bộ (self-signed) + ghi chú rõ không thay
     CA"** (mức trung dung, KHÔNG chọn tích hợp CA thật — việc đó cần hợp đồng với bên thứ 3, ngoài phạm
     vi 1 task code).
3. **Logo/letterhead**: user chọn **"Tạm dùng header text"** (tên đơn vị dạng text, để trống ô đóng dấu
   tay) — không chặn tiến độ chờ file logo thật.
4. **Thư viện PDF**: user chọn **"pdfmake"** (thuần JS, không cần Chromium headless, nhẹ hơn Puppeteer,
   hỗ trợ nhúng font TrueType tiếng Việt) — KHÔNG chọn Puppeteer.

### "Ký nội bộ" — `shared/utils/pdfSignature.util.ts` (MỚI)
- 1 cặp khoá RSA-2048 DÙNG CHUNG toàn hệ thống (không phải khoá riêng từng user) — vì tại thời điểm
  duyệt (`approveStep`/`rejectStep`), người duyệt KHÔNG hề nhập mật khẩu/PIN nào để "ký" — chỉ có
  role+userId+timestamp ghi vào `WorkflowInstance.steps`. "Ký" ở đây nghĩa là HỆ THỐNG xác nhận dữ liệu
  trong PDF khớp đúng dữ liệu DB tại thời điểm xuất, KHÔNG PHẢI "người duyệt X tự tay ký".
- `signPayload`/`verifySignature` dùng Node `crypto` built-in (`createSign`/`createVerify`,
  RSA-SHA256) — KHÔNG thêm dependency crypto ngoài (Node có sẵn đủ dùng).
- Khoá đọc từ env (`PDF_SIGN_PRIVATE_KEY`/`PDF_SIGN_PUBLIC_KEY`, PEM encode base64 để giữ 1 dòng .env),
  cache lazy trong module — KHÔNG làm app crash lúc khởi động nếu chưa cấu hình, chỉ throw rõ ràng khi
  THỰC SỰ gọi xuất PDF mà thiếu khoá.
- `scripts/generate-pdf-signing-keys.ts` (MỚI, KHÔNG track git — `backend/.gitignore` loại trừ
  `scripts/`) — sinh khoá 1 lần/môi trường, đã chạy cho DB dev và dán vào `.env` cục bộ.

### PDF service — `services/documents/documentPdf.service.ts` (MỚI)
- `exportDocumentPdfService(documentId, actorUserId)`:
  1. Load Document (active) + populate `department`/`createdBy`.
  2. Load `WorkflowInstance` qua `document.workflowInstanceId` (nếu có), populate `steps.approvedBy`.
  3. Build payload canonical (chỉ field THỰC SỰ hiển thị trong PDF) → hash SHA-256 → ký bằng khoá hệ
     thống → lưu 1 bản ghi `DocumentPdfExport` (audit, KHÔNG sửa/xoá).
  4. Build `docDefinition` pdfmake: header đơn vị (text, `ORG_DISPLAY_NAME` env, fallback "ĐƠN VỊ Y TẾ")
     + thông tin Document + "Nội dung" (rẽ nhánh theo `subType`, xem dưới) + "Phê duyệt" (bảng từ
     `WorkflowInstance.steps`) + khối "Xác thực nội bộ hệ thống" (mã xác thực = `DocumentPdfExport._id`,
     QR code — dùng lại package `qrcode` ĐÃ CÓ SẴN trong repo cho Asset QR, không thêm dependency mới —
     kèm CHÚ THÍCH RÕ RÀNG không phải chữ ký số CA).
  5. `pdfMake.createPdf(docDefinition).getBuffer()` → trả `Buffer` cho controller.
- Rẽ nhánh "Nội dung" theo `subType` — ĐỒNG BỘ THỦ CÔNG với nguồn sự thật phía FE
  (`documentMeta.ts::getMetaShape`, không import chéo được vì 2 codebase riêng — đổi 1 bên phải soát lại
  bên kia):
  - `PROPOSE_REPAIR` → text `meta.issue` (+ `repairResult` nếu có).
  - `PROPOSE_INK`/`PROPOSE_PROCUREMENT` → bảng `meta.items[]` (deviceName/quantity/unitPrice/totalPrice/
    note) + `totalAmount`.
  - `CHECK_DAMAGE`/`CONFIRM_STATUS` → `inspectionResult` + bảng `meta.items[]` (description/quantity/
    unitPrice/totalPrice).
  - Còn lại (MANUAL, hoặc meta bất thường ở subType khác) → fallback dump key-value thô (JSON pretty),
    GIỐNG HỆT fallback phía FE (`DocumentMetaView.tsx`).
- `verifyDocumentPdfExportService(exportId)` — load bản ghi `DocumentPdfExport`, `verifySignature
  (contentHash, signature)` bằng khoá công khai hệ thống, trả `{valid, documentId, exportedBy,
  exportedAt, algorithm, disclaimer}`. CHỈ xác minh signature khớp đúng hash ĐÃ LƯU (không tính lại hash
  từ dữ liệu DB hiện tại — nếu Document đổi sau khi xuất, `valid` vẫn `true` vì bản ghi export đó vẫn
  đúng với CHÍNH NÓ tại thời điểm xuất, không đại diện cho dữ liệu hiện tại).

## 5. Bug thật phát hiện SAU khi báo DONE lần đầu — user test qua trình duyệt

User bấm "Xuất PDF" trên `DocumentDetailPage` (tài liệu `RP-KKBĐK - HSCC-2026-0105`, subType
CONFIRM_STATUS) → nhận lỗi 500 chung chung, gửi kèm ảnh chụp Network tab. **Ban đầu nghi ngờ do server
dev chưa nạp lại `.env` mới** (giả thuyết hợp lý nhưng SAI) — sau khi user xác nhận "vẫn lỗi" dù đã
restart, đã tái hiện lỗi TRỰC TIẾP bằng script gọi `exportDocumentPdfService` với ĐÚNG document đó qua
`ts-node` — service tự nó chạy OK. Từ đó thu hẹp phạm vi xuống lớp controller (chỗ duy nhất chưa được
service-level test chạm tới) và tái hiện chính xác:

- **Root cause (CONFIRMED, không phải suy đoán)**: `documentPdf.controller.ts` set
  `res.setHeader("Content-Disposition", `attachment; filename="${fileName}"`)` với `fileName =
  documentCode + ".pdf"`. HTTP header value chỉ chấp nhận ISO-8859-1 (Node tự validate qua
  `checkInvalidHeaderChar`, regex cho phép `\t, \x20-\x7e, \x80-\xff`) — `documentCode` THẬT hầu hết có
  dấu tiếng Việt (VD "Đ" = U+0110, ngoài dải 0xff) → `res.setHeader` ném `TypeError [ERR_INVALID_CHAR]`
  NGAY KHI GỌI, rơi xuống `catchAsync` → lỗi 500 generic ("Đã có lỗi xảy ra, vui lòng thử lại sau" —
  `error.middleware.ts` dòng ~202, đúng message user thấy trên UI).
  - Đã verify bằng script Node độc lập: gọi `res.setHeader` với chính chuỗi "RP-KKBĐK - HSCC-2026-0105.pdf"
    → tái hiện CHÍNH XÁC `ERR_INVALID_CHAR`.
  - Đây là bug MỚI, KHÔNG có ở `excel.service.ts`/`assetExcel.service.ts`/`userAudits.service.ts` (đã
    soát) — 3 chỗ đó CỐ Ý dùng filename cố định thuần ASCII (`Danh-sach-...`, `Audit-log_...`). PDF export
    là chỗ ĐẦU TIÊN trong repo nhét dữ liệu thật (`documentCode`) vào filename → lỗ hổng test coverage:
    `documentPdf.service.test.ts` chỉ assert `result.fileName` ĐÚNG GIÁ TRỊ, không bao giờ chạm tới bước
    dựng HTTP header (nằm ở controller).
- **Fix**: dùng package `content-disposition` (ĐÃ CÓ SẴN qua Express như transitive dependency — giờ khai
  báo trực tiếp trong `package.json`/`@types/content-disposition` ở devDependencies, KHÔNG tăng thêm
  dung lượng cài đặt) thay vì tự nối chuỗi — tự mã hoá đúng chuẩn RFC 6266
  (`filename="<ascii-fallback>"; filename*=UTF-8''<percent-encoded>`), browser hiện đại hiển thị đúng tên
  tiếng Việt, client cũ fallback về bản ASCII an toàn.
- **Test mới**: `controllers/documents/__tests__/documentPdf.controller.test.ts` (2 test, MỚI — file
  controller test ĐẦU TIÊN trong repo, mọi test khác đều ở tầng service; thêm riêng vì bug nằm ĐÚNG ở
  lớp controller, service test không bao giờ chạm tới). Đã tự verify test THẬT SỰ bắt được bug (không
  phải test giả positive): revert tạm về code lỗi → test 2 FAIL đúng như kỳ vọng → khôi phục lại fix →
  PASS lại.
- Backend sau fix: **331/331 test PASS** (329 + 2 mới).
