# DEV-045 — TOCTOU: dò trùng đề xuất sửa chữa Asset (RV05-07)

> Ngày: 2026-09-12. Status: **DONE**. Nguồn gốc: user yêu cầu trực tiếp — việc #2/5 trong danh sách "Backend Open Risks" (`docs/30_DEVELOPMENT_COMPLETION_AUDIT.md` Mục 3/9), cùng họ lỗi với `ARCH-21` đã fix ở `excel.service.ts` (DEV-025) nhưng chưa từng được áp dụng cho domain Document/Asset.

## Objective

`createDocumentService()` (nhánh `PROPOSE_REPAIR`) chặn tạo đề xuất sửa chữa TRÙNG LẶP cho cùng 1 Asset khi đề xuất trước còn `workflowStatus: "pending"`. Check này trước đây đọc NGOÀI transaction — 2 request đồng thời cho CÙNG 1 asset có thể cùng vượt qua check rồi cùng được tạo, dẫn tới 2 workflow độc lập tranh nhau đổi trạng thái 1 asset khi duyệt xong.

## Root Cause (evidence-based, HIGH confidence)

**File**: `backend/src/services/documents/document.service.ts`, function `createDocumentService()`.
```ts
// TRƯỚC (bug):
const pendingProposal = await findPendingRepairProposalForAsset(relatedAsset); // NGOÀI transaction
if (pendingProposal) throw ApiError.badRequest(...);
...
const doc = await withTransaction(async (session) => {
  const created = await createDocument({...}, session);
  ...
});
```
Window TOCTOU giữa lúc đọc (`findPendingRepairProposalForAsset`) và lúc ghi (`createDocument` trong transaction riêng) — 2 request chạy gần như đồng thời đều đọc "chưa có pending nào" trước khi request nào kịp ghi, dẫn tới cả 2 đều tạo mới thành công.

**Cùng họ lỗi với `ARCH-21`** (đã fix ở `excel.service.ts`/`importDocumentsExcel`, DEV-025, 2026-09-XX) — cách vá đã được kiểm chứng, review, có regression test riêng (`excel.service.test.ts`). `docs/30_DEVELOPMENT_COMPLETION_AUDIT.md` Mục 3 xác nhận lại RV05-07 vẫn CÒN TỒN TẠI, chưa từng có DEV-XXX xử lý cho domain Asset.

## Fix (đồng bộ đúng pattern `ARCH-21`, không sáng chế cơ chế mới)

### 1. `backend/src/services/documents/documents.query.ts`
`findPendingRepairProposalForAsset(assetId, session?)` — thêm tham số `session` optional, gắn `.session(session ?? null)` vào query.

### 2. `backend/src/services/documents/document.service.ts`
`createDocumentService()` — RÚT check trùng lặp ra khỏi nhánh validate (giữ lại: bắt buộc `relatedAsset`, Asset tồn tại, Asset không DISPOSED/LOST — 3 check này KHÔNG có tính đua tranh tương tự nên giữ nguyên ngoài transaction, đúng phạm vi finding RV05-07 chỉ nói về check TRÙNG LẶP). Check trùng lặp chuyển vào **NGAY ĐẦU callback `withTransaction`**, đọc qua `session`:
```ts
const doc = await withTransaction(async (session) => {
  if (subType === DocumentSubType.PROPOSE_REPAIR) {
    const pendingProposal = await findPendingRepairProposalForAsset(relatedAsset, session);
    if (pendingProposal) throw ApiError.badRequest(...);
  }
  const created = await createDocument({...}, session);
  ...
});
```
**Đánh đổi CHỦ Ý, ghi rõ trong code**: `documentCode` vẫn cấp phát TRƯỚC transaction (dùng chung cho MỌI loại document, không riêng PROPOSE_REPAIR — không di dời để tránh mở rộng phạm vi sửa) — nếu nhánh trùng lặp throw, mã đó bị bỏ phí (khoảng trống đánh số). Đây là hệ quả PHỤ chấp nhận được (chỉ ảnh hưởng thẩm mỹ đánh số, không ảnh hưởng tính đúng đắn dữ liệu).

## Review

- Scope tối thiểu: chỉ di chuyển ĐÚNG 1 câu query (dò trùng lặp) vào trong transaction — không đụng 3 check khác (relatedAsset bắt buộc/Asset tồn tại/Asset không DISPOSED-LOST), không đụng `documentCode` generation (dùng chung mọi loại document).
- Tái sử dụng NGUYÊN VẸN pattern đã kiểm chứng ở ARCH-21 (`.session(session)`, đọc trong callback, throw rollback toàn bộ) — không phát minh cơ chế mới.
- Test mới dùng ĐÚNG kỹ thuật regression-guard đã có ở `excel.service.test.ts` (so sánh `invocationCallOrder`) để tự động phát hiện nếu sau này ai vô tình đưa check ra ngoài transaction lại.
- **Giới hạn đã biết, không phải lỗi mới**: cách vá này (đọc trong transaction, snapshot isolation) làm SNAPPING race window rất hẹp trong thực tế nhưng KHÔNG phải là ràng buộc tuyệt đối 100% ở tầng MongoDB (transactions không tự động serialize 2 lần "check rồi insert MỚI" nếu không có unique index) — cùng giới hạn lý thuyết với chính fix ARCH-21 gốc đã chấp nhận. Giải pháp triệt để hơn (unique index) là thay đổi schema, rủi ro cao hơn (cần audit dữ liệu cũ trước), NGOÀI phạm vi task này.
