# DEV-108 — BR-22: Upload controller dùng `catchAsync` + `ApiError`, format lỗi chung

**Ngày:** 2026-09-30
**Trạng thái:** DONE
**Loại:** REFACTOR (đồng bộ error handling) + BUG FIX nhỏ (upload không kèm file)

**Nguồn:** `docs/31_BACKEND_CODE_REVIEW.md` BR-22 (LOW).

## 1. Hiện trạng trước khi sửa

`controllers/upload/upload.controller.ts` là controller duy nhất không đi qua `catchAsync`/`ApiError`:

- Mọi lỗi 403/404 trả `res.status(...).json({ message })` — **thiếu `success:false` và `errorCode`** so với format chung của `errorHandler` (`{success:false, message, errorCode}`).
- `uploadFiles` tự `try/catch`, trả 500 `{ message }` riêng (ghi chú cũ ở đó nói "đồng bộ hoá là ARCH-09, ngoài phạm vi").
- Lỗi thật: gửi `POST /api/upload` **không kèm file** (vd body JSON, `req.files` là `undefined`) → `files.map` văng TypeError → 500 chung, không có thông báo hữu ích. (Chưa kiểm chứng riêng trên code cũ trường hợp multipart chỉ có field text; code mới chặn cả `undefined` lẫn mảng rỗng.)
- Message lệch nhau: có lỗi chính tả `"Không timg thấy file"`, có tiếng Anh `"File not found"`/`"File deleted"`.

## 2. Quyết định của user (AskUserQuestion)

- Không kèm file → **trả 400 rõ ràng** (không giữ 500).
- **Sửa chính tả + thống nhất tiếng Việt** cho các message.

## 3. Thay đổi

`controllers/upload/upload.controller.ts` (5 handler, cùng đường dẫn/permission/middleware, không đụng route):

- Cả 5 handler bọc `catchAsync`; mọi `return res.status(4xx).json({message})` → `throw ApiError.notFound/forbidden/badRequest(...)`. `try/catch` riêng của `uploadFiles` được bỏ — lỗi bất ngờ đi qua `errorHandler` (log có cấu trúc, message generic không lộ chi tiết nội bộ, đã làm ở DEV-021/SEC-23).
- `uploadFiles`: không có file (`req.files` undefined hoặc rỗng) → `ApiError.badRequest("Vui lòng chọn ít nhất 1 file để tải lên")` → 400 `BAD_REQUEST`.
- Message: `"Không timg thấy file"` → `"Không tìm thấy file"`; `"File not found"` → `"Không tìm thấy file"`; `"File deleted"` → `"Đã xoá file"`. Các message 403 và `"File đã được xóa rồi"`, `"File thiếu dữ liệu…"`, `"File không còn tồn tại trên server"`, `"Upload success"` giữ nguyên.

**Không đổi:** route, permission (`UPLOAD_FILES`/`VIEW_FILES`/`VIEW_FILE_DETAIL`/`DELETE_FILE`), guard chủ sở hữu/ADMIN, response thành công (`{success, message?, data?}`), status code các nhánh cũ (404/403 giữ nguyên), service, model, frontend.

**Response lỗi đổi (thêm field, không bỏ field nào):** `{ message }` → `{ success:false, message, errorCode }`, với `errorCode` = `BAD_REQUEST` / `FORBIDDEN` / `NOT_FOUND` / `UNKNOWN_ERROR`. Frontend chỉ đọc `message` (`parseApiError`), nên không ảnh hưởng.

**500 bất ngờ:** message đổi từ `"Đã có lỗi xảy ra khi upload file, vui lòng thử lại sau"` sang message generic chung `"Đã có lỗi xảy ra, vui lòng thử lại sau"` (cùng mọi route khác).

OpenAPI (`openAPI.yaml`, nhóm `/api/upload*`): 7 schema lỗi inline `{message}` → `$ref ErrorResponse`; mô tả POST bổ sung ca "không kèm file → 400" và format lỗi chung; mô tả 500 cũ ("module này chưa dùng ApiError", "sai `allowedTypes`") đã lỗi thời (sai loại file là 400 từ DEV-017) → viết lại. `docs/frontend/API_REFERENCE.md` bổ sung ghi chú.

## 4. Impact

- API: chỉ thêm field lỗi + 1 ca mới 400 (trước là 500). Database: không. Security/RBAC: không đổi; đã xác nhận lại 401/403 ở cả 5 route (Mục 5).
- Frontend: không đổi (không cần build lại). Playwright 16/16 vẫn chạy.

## 5. Test

E2E mới `__tests__/e2e/upload-error-format.e2e-test.ts` (20 test, HTTP thật + multer ghi đĩa thật + MongoDB in-memory; file thử mang tiền tố `br22-e2e-`, xoá ở `afterAll`, đã kiểm tra thư mục `uploads/` sạch):

- Xác thực/phân quyền: không token → 401 trên cả 5 route; user thiếu permission → 403 trên cả 5 route.
- Upload: thành công giữ nguyên format; **không kèm file** (multipart chỉ có field text, và body JSON) → 400 và không lưu gì; lỗi DB bất ngờ (mock `Upload.insertMany` reject) → 500 `UNKNOWN_ERROR` message generic, không lộ chuỗi lỗi nội bộ.
- Xem/tải/xoá: chủ sở hữu 200, ADMIN 200, người khác (role thường có đủ 4 permission file, tạo riêng trong test vì seed chỉ cấp quyền file cho ADMIN) → 403 `FORBIDDEN`; id không tồn tại → 404 tiếng Việt; id sai định dạng → 400; xoá mềm rồi xem/tải → 404 "đã được xóa"; tải file thật đúng nội dung, xoá file khỏi đĩa → 404 "không còn tồn tại"; bản ghi thiếu `fileUrl` → 404.
- Danh sách: format `{success, data, pagination}` giữ nguyên, người khác không thấy file của chủ; `limit=abc` vẫn 400.

**Đã kiểm chứng test bắt được lỗi:** chạy bộ test này trên controller CŨ (trước khi sửa): **11 fail / 9 pass** (thiếu `success`/`errorCode`, message cũ, không-file trả 500); sau khi sửa: 20/20 pass. Không cần revert lại vì baseline chạy trước khi áp dụng sửa.

Toàn bộ: `tsc` 0 lỗi, unit 53 suites / 562 tests (không đổi), e2e 27 suites / 178 tests (+20), `npm run build` PASS, Playwright 16/16. Không có unit test riêng cho controller (dự án kiểm bằng e2e).

## 6. Ghi nhận, chưa sửa (ngoài phạm vi)

- `deleteFile` không kiểm tra `isDeleted`: xoá lại file đã xoá vẫn trả 200 (hành vi cũ, idempotent).
- Nếu lưu DB thất bại SAU khi multer đã ghi file, file mồ côi còn trên đĩa (đã thấy khi test lỗi DB; test dọn theo tiền tố). Cần task riêng nếu muốn dọn tự động.
- Mọi lỗi đi qua `errorHandler` giờ được `console.error` kèm stack (kể cả 403/404 bình thường) — đó là hành vi chung của `errorHandler` cho mọi route, không riêng Upload.
- `docs/03_BACKEND_ANALYSIS.md` và `docs/module-reviews/09_UPLOAD_CODE_REVIEW.md` là tài liệu lịch sử mô tả controller cũ ("KHÔNG có field success", `File deleted`); giữ nguyên làm lịch sử, DEV-108 là bản hiện hành.
