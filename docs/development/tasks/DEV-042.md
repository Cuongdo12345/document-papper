## F1 — `grep -rn 'setQueryData(\["users","me"\]' src/`

**Lệnh gốc trả về rỗng** — vì code KHÔNG viết literal `["users","me"]` mà dùng hằng số dùng chung `CURRENT_USER_QUERY_KEY` (định nghĩa ở `src/hooks/useCurrentUser.ts:11`, giá trị = `["users", "me"] as const`). Chạy lại broader (`grep -rln 'setQueryData' src/`) để không bỏ sót:

```
src/features/auth/hooks/useLogin.ts
src/features/profile/hooks/useUpdateProfile.ts
```

Đọc trực tiếp cả 2 file:

- **`useLogin.ts`** — GỌI THẬT `queryClient.setQueryData(CURRENT_USER_QUERY_KEY, user)` (seed cache tạm bằng `user` subset từ response login, không đợi gọi `GET /users/me` riêng) → **NGAY DÒNG SAU** gọi `queryClient.invalidateQueries({ queryKey: CURRENT_USER_QUERY_KEY })`. Có comment giải thích chi tiết (dated 2026-09-09, FE-09): `user` từ login là SUBSET thiếu `permissions[]`/`role.isSystemRole`, nếu không invalidate thì mọi permission check sai trong 60s đầu (do `staleTime:60_000`) — đây CHÍNH LÀ fix cho đúng loại bug mà lệnh grep F1 đang dò tìm, đã được xử lý từ trước.
- **`useUpdateProfile.ts`** — grep khớp vì có dòng COMMENT chứa chữ "setQueryData" ("KHÔNG `setQueryData` bằng response... để refetch lại `["users","me"]` đầy đủ"), KHÔNG PHẢI code thật. File này chỉ gọi `invalidateQueries` (không set cache tay) — đúng ý định mô tả trong comment.

**Kết luận**: Toàn bộ codebase hiện tại chỉ có **đúng 1 chỗ** set cache "users/me" thủ công, và chỗ đó **CÓ** invalidate kèm ngay lập tức trong cùng khối `onSuccess`. Không phát hiện lỗ hổng.

## F4 — `grep -rn 'isSystemRole' src/features/rbac/`

```
src/features/rbac/hooks/useRoles.ts:27-29    (comment)
src/features/rbac/pages/RolesListPage.tsx:62  (cột bảng)
src/features/rbac/pages/RolesListPage.tsx:130 (comment)
src/features/rbac/utils/roleGuards.ts:4,6,8,13,15,16  (định nghĩa hàm)
```

Đọc trực tiếp 3 file liên quan:

1. **`roleGuards.ts`** — định nghĩa DUY NHẤT:
   ```ts
   export function isProtectedSystemRole(role: Pick<Role, "isSystemRole" | "name">): boolean {
     return role.isSystemRole === true || role.name === "ADMIN";
   }
   ```
2. **`RolesListPage.tsx`** (dòng 64) và **`RoleDetailPage.tsx`** (dòng 113) — **cả 2 đều import và gọi ĐÚNG hàm này** (`isProtectedSystemRole(row)` / `isProtectedSystemRole(role)`) để ẩn nút Sửa/Xoá + hiện badge "System Role". → **Giống hệt nhau, đúng như câu hỏi F4 kỳ vọng.**
3. **`useRoles.ts`** (`useAssignableRoles`) — có 1 chỗ THỨ 3, viết TAY lại logic tương đương (phủ định, đúng De Morgan): `!r.isSystemRole && r.name !== "ADMIN"`, KHÔNG import `isProtectedSystemRole`. Đây KHÔNG phải sơ suất — cả 2 file có comment CHÉO giải thích rõ:
   - `useRoles.ts:27-29`: "ADMIN/isSystemRole, backend chặn cứng gán role này... `role.isSystemRole===true || role.name==="ADMIN"`"
   - `roleGuards.ts:8-11`: "`useRoles.ts` (`useAssignableRoles`, FE-03) đã áp dụng ĐÚNG dual-check này. Hàm này (`isProtectedSystemRole`, FE-08) tái dùng CÙNG LOGIC cho RBAC Admin UI"
   
   → `useAssignableRoles` (FE-03) có TRƯỚC, `isProtectedSystemRole()` (FE-08) được viết SAU, cố ý dùng lại đúng công thức thay vì gọi lại hàm cũ — nhưng KHÔNG hợp nhất về 1 hàm duy nhất.

**Kết luận**: 2/3 nơi dùng CHUNG 1 hàm (đúng câu hỏi F4 — giống nhau, xác nhận AN TOÀN). Phát hiện thêm 1 nơi thứ 3 (`useAssignableRoles`) trùng logic nhưng viết tay lại — rủi ro THẤP (đã tự ghi chú chéo, tương đương toán học đã tự kiểm), nhưng vẫn là 1 điểm có thể lệch trong tương lai nếu điều kiện đổi ở 1 nơi mà quên nơi kia (VD sau này `isSystemRole` migrate xong, chỉ cần bỏ `|| role.name === "ADMIN"` ở ĐÚNG 1 chỗ — nếu sửa `roleGuards.ts` mà quên `useRoles.ts`, 2 nơi sẽ lệch nhau). **Đề xuất nhỏ (chưa làm, ngoài phạm vi yêu cầu hiện tại)**: đổi `useAssignableRoles` sang gọi `!isProtectedSystemRole(r)` thay vì viết tay, gộp về đúng 1 nguồn.

## F5 — `grep -rn '\.permissions\.includes(' src/ | grep -v 'usePermission\|permissionCheck'`

**Lệnh gốc trả về rỗng.** Chạy lại broader (bỏ điều kiện loại trừ, đổi pattern để bắt cả biến không tên `permissions` gắn `.`):

```
src/utils/permissionCheck.ts:12:  return list.some((p) => permissions.includes(p));
src/utils/permissionCheck.ts:16:  return required.some((p) => permissions.includes(p));
src/utils/permissionCheck.ts:20:  return required.every((p) => permissions.includes(p));
```

Cả 3 match duy nhất trong toàn bộ `src/` đều nằm NGAY BÊN TRONG `permissionCheck.ts` — đúng là 3 hàm thuần (`checkHasPermission`/`checkHasAnyPermission`/`checkHasAllPermissions`) mà `usePermission()` gọi lại (tách riêng khỏi React để unit-test trực tiếp, theo comment đầu file). Không có bất kỳ component/page nào tự viết `.includes()` để tự check permission ngoài luồng này.

**Kết luận**: Không phát hiện chỗ nào bypass `usePermission()`/`permissionCheck.ts`. An toàn.

## F7 — `grep -rn 'StatusBadge' src/ | grep -i 'status'`

Danh sách đầy đủ ở output gốc (46 dòng) — tóm tắt cấu trúc:

**5 wrapper "mapping riêng theo domain"** (mỗi cái tự định nghĩa bảng map enum → `variant`/label, rồi render `<StatusBadge variant={...}>`):

**Kết luận**: Xác nhận ĐÚNG câu hỏi F7 — có pattern nhất quán: enum có ≥3 giá trị/màu phức tạp → tách wrapper domain riêng (dễ tái sử dụng, dễ test); enum nhị phân đơn giản → dùng thẳng `StatusBadge` inline (không over-engineer tạo wrapper cho 2 giá trị). Đây là CONVENTION có chủ đích, không phải trùng lặp tuỳ tiện — khớp nguyên tắc "No Over-Engineering" (CLAUDE.md Mục 12).
