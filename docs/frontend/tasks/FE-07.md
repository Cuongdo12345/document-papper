# FE-07 — Medical Devices UI

> Ngày: 2026-09-07. Status: **DONE**. Nguồn gốc: tiếp nối roadmap sau FE-06 (Assets Core UI) — user yêu cầu trực tiếp "Tiếp tục làm phase UI tiếp theo nhé". Thứ tự roadmap (`FE_UI_DEVELOPMENT_ROADMAP.md` Mục 29): Assets → **Medical Devices** → RBAC Admin → Dashboard → ...

## Objective

Xây dựng UI cho hồ sơ thiết bị y tế (phân loại pháp lý, giấy phép lưu hành) và lịch sử kiểm định/hiệu chuẩn — theo scope Mục 13 roadmap ("Medical Devices UI"): "device identity, calibration status, calibration records, dates, next calibration, history".

## Quyết định thiết kế quan trọng: KHÔNG có route/trang riêng

Khác Assets/Documents (đều có `/list`, `/create`, `/:id` riêng), Medical Device UI **nhúng thẳng vào `AssetDetailPage`** (FE-06), KHÔNG tạo route `/app/medical-devices/*` nào. Lý do (evidence-based, không phải quyết định tuỳ ý):

- Backend tự thiết kế theo đúng hướng này — MỌI endpoint đều theo `:assetId` (`medicalDevice.routes.ts`), KHÔNG có `profileId` riêng để định danh 1 route độc lập.
- `MedicalDeviceProfile` là quan hệ 1-1 với `Asset` (`index({asset:1},{unique:true})`) — "gắn thêm 1 lớp thông tin cho 1 Asset đã có", không phải 1 domain resource độc lập.
- Comment sẵn có trong chính source backend (`medicalDeviceAlerts.service.ts`): *"MedicalDeviceProfile không có màn hình chi tiết riêng ở FE, mọi thao tác đều thực hiện qua màn hình chi tiết Asset"* — khớp CHÍNH XÁC gợi ý ở roadmap Mục 13: "Medical Device Profile là sub-feature nghiệp vụ nhưng UI có thể dùng section/tab trong asset detail nếu phù hợp".

## Scope quyết định loại trừ (giống tinh thần FE-06)

- **Upload file chứng nhận kiểm định thật** (`certificateFile`, multipart — "Giai đoạn 5" backend) — CHƯA làm, chỉ hỗ trợ `certificateFileUrl` dạng link nhập tay (JSON thuần, DTO backend đã hỗ trợ sẵn không cần sửa gì). Lý do: cần `FileUpload` component dùng chung — thuộc phase riêng "Upload/Excel UI" (roadmap Mục 20), chưa xây ở bất kỳ domain nào trong FE tính tới giờ (xác nhận `grep` không ra file nào).
- **Sửa/xoá 1 bản ghi kiểm định cụ thể** — backend KHÔNG có endpoint này (chỉ Create + list History, đúng chủ đích "bằng chứng thanh tra", append-only) — không tự thêm UI cho tính năng không tồn tại.
- **Cảnh báo kiểm định** (`POST /alerts/run`) — hành động vận hành (cron trigger tay), không thuộc phạm vi "xem/quản lý 1 thiết bị cụ thể" — để dành cho phase Dashboard/Notifications sau nếu cần UI riêng.

## Root cause / Evidence trước khi code

- `frontend/src/features/assets/pages/AssetDetailPage.tsx` (FE-06) có sẵn comment tự ghi: *"Medical Device Profile/Calibration CHỦ Ý CHƯA có ở trang này (roadmap Mục 13 — phase riêng)"* — xác nhận đúng vị trí cần bổ sung.
- Backend domain đã đầy đủ (đọc trực tiếp `medicalDevice.routes.ts`/`.controller.ts`/`.service.ts`, `calibrationRecord.*`, `medicalDeviceProfile.model.ts`, `calibrationRecord.model.ts`, `medicalDeviceAlerts.service.ts`) — không cần sửa backend cho scope task này.
- Ngưỡng "sắp tới hạn kiểm định" (30 ngày) lấy TRỰC TIẾP từ hằng số `CALIBRATION_ALERT_DAYS_BEFORE` (`medicalDeviceAlerts.service.ts:24`) — không tự bịa số khác backend, đảm bảo UI và cron cảnh báo nhất quán.

**Lỗi phát hiện qua build**: `z.enum(X as [T, ...T[]])` với `X` khai `as const` (readonly tuple) gây lỗi type "readonly không gán được vào mutable tuple" — khác `CREATABLE_SUB_TYPES` (Document, khai kiểu mutable `T[]`) nên cast đó từng chạy được. Sửa: bỏ cast thừa, truyền thẳng mảng `as const` vào `z.enum()` (zod tự nhận đúng kiểu readonly tuple).
