# FE-08 — RBAC Admin UI

> Ngày: 2026-09-07. Status: **DONE**. Nguồn gốc: tiếp nối roadmap sau FE-07 (Medical Devices UI) — user yêu cầu trực tiếp "tiếp tục làm phase tiếp theo RBAC Admin UI". Thứ tự roadmap (`FE_UI_DEVELOPMENT_ROADMAP.md` Mục 29): Medical Devices → **RBAC Admin** → Dashboard → ...

## Objective

Xây dựng UI quản trị RBAC đầy đủ theo scope Mục 16 roadmap: "UI gồm Roles/Permissions/Policies. Ưu tiên: permission matrix, role detail, policy detail, clear read/write/action separation, warning trước destructive change." Trước task này, `features/rbac/` CHỈ có `useRoles()` (list-only, phục vụ dropdown chọn role ở Users UI FE-03) — chưa có CRUD thật nào.

## Root cause / Evidence trước khi code

- Backend đã có ĐẦY ĐỦ CRUD cho cả 3 resource (`rbac.routes.ts`/`rbac.controller.ts`/`rbac.service.ts`) — không cần sửa backend cho scope task này.
- `ROUTE_PERMISSION_MAP.md` (viết trước, ở giai đoạn phân tích) đã đề xuất sẵn 3 route `/rbac/{roles,permissions,policies}` — dùng đúng path đó thay vì tự đặt path khác.
- **Phát hiện tài liệu OUTDATED** (CLAUDE.md Mục 3 — source code/behavior thật ưu tiên hơn tài liệu cũ): `ROUTE_PERMISSION_MAP.md` ghi chú Policies "cân nhắc ẩn/gắn Beta — cơ chế ABAC chưa hoạt động runtime". Ghi chú này SAI so với thực tế hiện tại — DEV-034 (task trước, cùng phiên làm việc) đã tạo + xác minh 1 Policy thật hoạt động đúng ở `authorizePermission.middleware.ts` (200 khi điều kiện khớp, 403 khi không, qua HTTP thật). Đã sửa ghi chú này (xem Mục "Documentation Sync" dưới) — Policies UI xây dựng như 1 tính năng hoạt động đầy đủ, KHÔNG gắn nhãn Beta.
- **Rủi ro đã kiểm tra trước khi code** (bài học DEV-034 cùng phiên: FE permission-gate có thể khoá nhầm cả role lẽ ra được phép): FE quy ước KHÔNG special-case ADMIN/`isSystemRole` khi tính `hasPermission()` (`hooks/usePermission.ts`, dựa 100% vào `user.permissions[]` từ `GET /users/me`). Đã verify TRƯỚC khi code: `rolePermission.map.ts` seed `ADMIN: [...Object.values(PERMISSIONS), "SYSTEM_ADMIN"]` — ADMIN có đủ `ROLE_VIEW`/`PERMISSION_VIEW`/`POLICY_VIEW`/... trong DB (xác nhận lại bằng HTTP thật ở Mục Tests, không chỉ đọc source). `ROUTE_PERMISSION_MAP.md` dòng `/users` cũng ghi "0 role thường giữ `USER_VIEW` → chỉ ADMIN xem được thực tế" — cùng pattern đã áp dụng thành công ở FE-03, không phải rủi ro mới.
- **Phát hiện thêm qua HTTP thật (không đoán trước được từ source)**: tài khoản `admin` ở DB hiện tại có `role.isSystemRole === false` — bypass Super-Admin CHỈ hoạt động qua nhánh OR `role.name === "ADMIN"` (migration DEV-001A "Phase A" chưa chạy xong ở environment này). Ảnh hưởng trực tiếp tới quyết định thiết kế UI — xem Mục "Đổi hướng khi code" dưới.

## Đổi hướng khi code (so với dự định ban đầu)

Ban đầu định ẩn nút Sửa/Xoá cho role bằng CHỈ `role.isSystemRole === true`. Verify live phát hiện role ADMIN thật có `isSystemRole: false` — nếu giữ nguyên, UI sẽ hiện nút Sửa/Xoá cho chính role ADMIN (bấm vào sẽ luôn nhận lỗi từ backend — không nguy hiểm vì backend vẫn chặn đúng, nhưng sai UX, ngược tinh thần roadmap "warning trước destructive change"). Sửa bằng cách tái dùng ĐÚNG dual-check backend đang tự dùng ở nhiều nơi (`role.isSystemRole===true || role.name==="ADMIN"`, xem `authorizePermission.middleware.ts` comment DEV-001A) — `useRoles.ts` (FE-03, code cũ) đã áp dụng đúng pattern này cho `useAssignableRoles()`, giờ tách thành helper dùng chung `isProtectedSystemRole()`.

## API Impact

Không đổi API/DTO/route backend nào — thuần FE consume API RBAC đã có sẵn.

## Security Impact

Không đổi RBAC/backend. UI đọc đúng permission hiện có để ẩn/hiện (`ROLE_*`/`PERMISSION_*`/`POLICY_*`) — backend vẫn là security boundary thật (đã tự verify: đổi tên/xoá role ADMIN đều bị backend chặn dù FE có bị bypass devtools). Đã kiểm tra riêng: `PolicyFormModal` không cho tạo policy với `condition` gọi hàm tuỳ ý — backend tự validate cú pháp (evaluator chống RCE, B1 review cũ), FE chỉ hiển thị lỗi đúng, không nới lỏng gì.
